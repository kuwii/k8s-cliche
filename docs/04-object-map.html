对象全景图

几十种对象不用背。分成六类，记住关系链，剩下的用到再查。

一句话答案

K8s 对象按职责分六类：工作负载、服务发现与负载均衡、配置与存储、集群治理、安全、元数据与扩展。

比对象清单更重要的是关系链：Deployment → ReplicaSet → Pod 是所有权链，Service → EndpointSlice → Pod 是选择链，PVC → PV 是绑定链。

为什么先分类

kubectl api-resources 会列出几十种资源，全背是徒劳的。分类的价值在于：遇到新对象时知道去哪个抽屉找它，并且能猜出它大概和谁有关系。

三条关系链

所有权链：Deployment → ReplicaSet → Pod

Deployment 不直接管 Pod。它管 ReplicaSet，ReplicaSet 管 Pod。中间这层的意义是滚动更新：新版本 = 新 ReplicaSet，旧的缩到 0 但保留，回滚就是切回去。

所有权由 ownerReferences 字段表达，它是级联删除的依据：删 Deployment，它的 ReplicaSet 和 Pod 会被垃圾回收一起删掉。第 01 章说「K8s 没有从属关系只有标签」——所有权是这句话的唯一例外补充：选择靠标签，生死靠 ownerReferences。

选择链：Service → EndpointSlice → Pod

Service 只存选择器；EndpointSlice 控制器把匹配且 Ready 的 Pod 写成后端列表。注意 Ready 这个条件——readiness 探针失败的 Pod 不在列表里，这是「Service 不通」的高频真凶（第 03 章误区五）。

绑定链：PVC → PV

PVC 是申请单，PV 是资源本体，绑定后 Pod 通过 PVC 用存储。细节见第 07 章。

三组最易混的对照

对照分界线
Deployment vs StatefulSet副本之间可否互换。可以（无状态）→ Deployment；不可以（每个副本有自己的身份和数据）→ StatefulSet
Deployment vs DaemonSet副本数由谁定。你定（要几份）→ Deployment；拓扑定（每节点一份）→ DaemonSet
Service vs Ingress四层 vs 七层。Service 是 IP:Port 级的稳定入口；Ingress 是域名/路径级的路由，且需要控制器实现

面试官视角

Q：说说 K8s 常见对象和它们的关系？

✕ 平庸答案

逐个念对象定义。

——没有结构，听完记不住，也看不出理解深度。

✓ 加分答案 · 分类 + 关系链

「我按职责分六类：工作负载、服务发现、配置存储、集群治理、安全、元数据与扩展。关系上最关键的是三条链：Deployment 通过 ReplicaSet 拥有 Pod，删除会级联；Service 通过选择器经 EndpointSlice 指向 Ready 的 Pod，这是选择关系不是所有权；PVC 绑定 PV 使用存储。理解『选择靠标签、生死靠 ownerReferences』这一句，大部分对象行为都能推出来。」

常见误区

误区一：直接用 ReplicaSet 管理应用

几乎从不。ReplicaSet 没有滚动更新能力。Deployment 是它的正确包装。

误区二：Pod = 一个容器

Pod 是「共享网络和存储卷的容器组」。单容器 Pod 是常见特例，不是定义。sidecar 模式正建立在多容器 Pod 之上。

误区三：Namespace 是安全隔离边界

默认只是名字与配额的作用域。Pod 间网络默认全通，跨 namespace 也能访问。真隔离要 NetworkPolicy + RBAC +（必要时）其他手段。
