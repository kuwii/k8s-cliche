网络

K8s 网络 = 三个问题：Pod 之间怎么通、外面怎么进来、名字怎么解析。

一句话答案

K8s 网络模型的基本假设：每个 Pod 有自己的 IP，Pod 之间无需 NAT 直接互通（由 CNI 插件实现）；Service 给一组 Pod 一个稳定虚拟 IP；CoreDNS 给 Service 一个稳定名字。

三层答案：CNI 管 Pod 互通，Service/Ingress 管入口，CoreDNS 管名字。

Pod 间互通：CNI 模型

K8s 只规定网络模型，不规定实现。模型要求：

  • 每个 Pod 拿到集群内唯一的 IP
  • 任意两个 Pod 可以直接通信（跨节点也一样），不需要 NAT
  • 节点与 Pod 之间也可以直接通信

实现这套模型的是 CNI 插件：Flannel（overlay 简单方案）、Calico（BGP/iptables，支持 NetworkPolicy）、Cilium（eBPF 数据路径）。IP 在 Pod 沙箱创建时分配（第 03 章 ⑤）。

同 Pod 内的容器共享沙箱网络：同一个 IP、互用 localhost、端口不能冲突——把它们想成同一台「小机器」上的进程。

Service：给易变的 Pod 一个不变的入口

Pod 会死会重建、IP 每次都变。Service 用选择器圈住一组 Pod，对外提供稳定的虚拟 IP（ClusterIP）和 DNS 名。

四种类型

类型暴露范围机制
ClusterIP（默认）仅集群内虚拟 IP + 内核转发规则
NodePort集群外，经任意节点 IP在 ClusterIP 基础上，每个节点开一个固定端口（默认 30000-32767）
LoadBalancer集群外，经云厂商 LB在 NodePort 基础上，向云申请外部负载均衡器
ExternalName—不做转发，只是 DNS CNAME 到外部域名

另有 headless Service（clusterIP: None）：不分配虚拟 IP，DNS 直接返回后端 Pod 的 IP 列表。StatefulSet 靠它给每个 Pod 独立域名（web-0.web.default.svc.cluster.local）。

流量路径：kube-proxy 不在路上

访问 ClusterIP 的包到达节点后，被内核的 netfilter（iptables 模式）或 IPVS 表做 DNAT，改写成某个后端 Pod 的 IP:Port 后直接发出。没有任何用户态进程经手这个包。

DNS：名字怎么变成 IP

CoreDNS 为每个 Service 创建记录：

# 完整域名（任何 namespace 内都可用）
web.default.svc.cluster.local

# 同 namespace 可简写
web

# 跨 namespace
web.default
  • 普通 Service：A 记录指向 ClusterIP
  • headless Service：A 记录直接指向各 Ready Pod 的 IP
  • 解析失败的高频原因不是 CoreDNS 挂了，而是 ndots:5 与 search 域导致的解析顺序问题——先用完整域名验证

Ingress：七层入口

NodePort/LoadBalancer 都是四层（IP:Port）。要按域名和路径路由（api.example.com → api 服务、/web → web 服务），需要七层——Ingress。

  • Ingress 对象：一组路由规则的声明
  • Ingress 控制器：真正干活的进程（nginx-ingress、traefik……），watch Ingress 对象并更新自己的路由配置
  • 控制器自己通常以 Deployment + LoadBalancer Service 暴露——七层建立在四层之上

TLS 终止也在这里：Secret 里放证书，Ingress 规则引用它。

NetworkPolicy：Pod 间防火墙

默认情况下集群内所有 Pod 互通——默认放行。NetworkPolicy 按标签选择 Pod，声明允许谁（from）以哪些端口（ports）访问它（ingress），或它允许访问谁（egress）。

两个关键点

① 一旦有任一策略选中某 Pod，该 Pod 未声明的方向即变为拒绝——默认放行变成默认拒绝，是按 Pod 逐个翻转的。② 策略要生效，CNI 插件必须支持（Flannel 不支持，Calico/Cilium 支持）。

面试官视角

Q：ClusterIP、NodePort、LoadBalancer 的区别？

✕ 平庸答案

「ClusterIP 集群内访问，NodePort 开端口，LoadBalancer 用云负载均衡。」

——对但薄。缺机制、缺叠加关系。

✓ 加分答案 · 叠加关系 + 数据路径

「三者是叠加关系：ClusterIP 是基础，一个只存在于内核转发规则里的虚拟 IP；NodePort 在它之上让每个节点监听一个固定端口；LoadBalancer 再在 NodePort 之上向云申请外部 LB。数据路径上三者都最终落到内核的 DNAT 规则，kube-proxy 只负责维护规则不在路径上。生产上对外入口更常用 Ingress 或 Gateway API，在七层做路由，避免为每个服务开一个 LB。」

Q：Pod 之间怎么通信？——答模型不答实现：每 Pod 独立 IP、扁平网络、无 NAT；实现交给 CNI（overlay / 路由 / eBGP / eBPF 各流派一句带过）；同 Pod 内容器共享沙箱网络。

常见误区

误区一：ClusterIP 是一个「真实存在」的 IP

没有任何网卡持有它。它只存在于每个节点的内核规则里，ping 不通是常态（除非规则恰好响应）。

误区二：Service 不通先查 Service 配置

先 kubectl get endpoints。后端为空（Pod 没 Ready / 标签没对上）远比 Service 配错常见。

误区三：装了 K8s 就有 NetworkPolicy

对象 API 存在 ≠ 生效。Flannel 等插件会接受对象但完全不执行。选型时就要确认。
