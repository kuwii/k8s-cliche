扩展机制

K8s 的扩展性不是特性列表，是三句话：加资源、加控制器、加关卡。

一句话答案

三种扩展点：CRD 注册新资源类型（数据面扩展），Operator = CRD + 控制器（把运维知识编码成控制循环），Admission Webhook 在请求路径上加自定义关卡（策略面扩展）。

它们复用的全是内置组件的同款机制——这正是第 01 章「一切皆资源」的红利。

CRD：往 API 里注册新资源

CustomResourceDefinition 让你定义自己的资源类型，比如 MySQLCluster。注册后：

  • kubectl get mysqlclusters 立刻可用——因为 kubectl 操作的是「资源」这个抽象，不关心内置与否
  • 对象存进 etcd、有 spec/status、能被 watch——全套机制免费获得
CRD 只是数据

只有 CRD 没有控制器时，你写的 MySQLCluster 对象躺在 etcd 里什么都不会发生。让它「活」起来的是控制器。

Operator：CRD + 控制器

Operator = 自定义资源 + 一个 watch 它并执行调谐的控制器。它把「DBA 的手艺」变成代码：创建 MySQLCluster 时自动起主从、配复制、做备份、故障切换。

典型例子：Prometheus Operator（声明 Prometheus 资源即部署监控）、cert-manager（声明 Certificate 即自动签证书续期）。

控制器是怎么写的：Informer 模式

  • Informer：对 API Server 做 List-Watch——先全量列一次建本地缓存，之后增量接收变更事件。控制器读的是本地缓存，不打 API Server
  • WorkQueue：事件入队、去重、限速、失败重试。同一个对象短时间变更十次，队列里只处理一次最新
  • Reconcile：从队列取 key，读期望与实际，做最小动作写回——就是第 01 章那个循环的工程形态

工具链定位：client-go 是底层库；controller-runtime 把 Informer/Queue/Manager 打包成易用抽象；kubebuilder / operator-sdk 是脚手架，生成 CRD 清单与控制器骨架。

Admission Webhook：请求路径上的自定义关卡

第 03 章 ① 站的准入阶段，除了内置逻辑，还可以调用你部署的 HTTPS 服务：

  • Mutating Webhook：可改写请求——自动注入 sidecar、补默认标签、拒绝+改写镜像来源
  • Validating Webhook：只裁决接受/拒绝——「生产 namespace 必须带 owner 标签」「limits 必须设置」这类组织策略

OPA Gatekeeper / Kyverno 就是「策略即数据」的通用 webhook 实现：策略写成声明式对象，不必为每条规则写代码。

什么时候才需要写 Operator

场景正确工具
部署一个普通应用Deployment + Service，别写 Operator
组织级准入策略Validating Webhook / Kyverno
应用有运维状态机：主从切换、备份、扩缩需要领域知识Operator
管理集群外部资源（云数据库、DNS 记录）Operator（控制器完全可以操作外部系统）

面试官视角

Q：什么是 Operator？/ Informer 的工作原理？

✕ 平庸答案

「Operator 就是管理应用的控制器。」

——同义反复。没说出 CRD、没说出调谐循环、没说出它和内置控制器的同构性。

✓ 加分答案

「Operator 是 CRD 加控制器的组合：CRD 把领域对象（如 MySQLCluster）变成 K8s 资源，控制器 watch 它并执行调谐循环，把运维知识——主从搭建、备份、故障切换——编码成代码。实现上靠 Informer 模式：List-Watch 建本地缓存，事件进 WorkQueue 去重，Reconcile 函数读缓存做最小变更写回。它和 Deployment 控制器用的是完全相同的机制，只是资源类型换成了自定义的。」

常见误区

误区一：写了 CRD 就等于有了功能

CRD 只注册了数据类型。没有控制器，对象只是 etcd 里的静态记录。

误区二：watch 是轮询

watch 是服务端推送的长连接。List 只发生一次（及断线重连/周期性 resync），稳态流量是增量事件流。

误区三：Operator 只能管集群内资源

控制器就是普通程序，完全可以调用云 API、操作外部数据库。「用 K8s API 管理云资源」正是 Operator 的高价值场景。
