K8s 是什么

在学「怎么用」之前，先搞清楚「它凭什么存在」。

一句话答案

Kubernetes 是一个声明式的容器编排系统：你告诉它「我想要什么状态」，它负责在一群机器上把容器跑起来、维持住、坏了修好、流量来了扩容。

它不是 Docker 的竞争者，而是 Docker 造出来的容器多到单机管不过来之后的答案。

为什么需要这一章

「容器编排平台」这个官方定义几乎不携带信息。什么叫编排？编什么？排什么？

这一章从问题出发：先看清楚没有 K8s 的世界长什么样、痛在哪里，K8s 的每个设计就都有了着落。知道它解决什么问题，比记住它有什么功能重要得多。

从一台机器说起：问题是怎么长出来的

容器之前

物理机时代：一个应用占一台机器。资源浪费（大部分机器利用率不到 15%）、部署慢（装机、装环境、上线以天计）、环境不一致（「在我电脑上是好的」）。

虚拟化时代：一台物理机切出多个虚拟机（VM）。隔离好了，但每个 VM 是一个完整操作系统——GB 级体积、分钟级启动，依旧笨重。

容器时代：Docker 把「容器」变成了易用品。容器共享主机内核，只是一个被隔离的进程——MB 级体积、秒级启动。更重要的是镜像（Image）：把应用和它的整个运行环境打包成一个标准件，在任何机器上跑出来都一样。

「在我电脑上是好的」这个问题，到此为止了。

但新的问题来了

容器太便宜了，于是你有了几十个容器、十几台机器。然后四个问题接踵而至：

  1. 放哪？十几台机器，每个容器该跑在哪一台？要考虑资源余量、故障分散、机架隔离……靠人排班表是不现实的。
  2. 怎么互相找到？容器随时可能死掉重建，IP 每次都变。前端怎么稳定地访问后端？
  3. 坏了怎么办？凌晨三点进程崩了，谁发现？谁重启？谁在机器整个宕机时把服务搬走？
  4. 流量变了怎么办？大促流量翻十倍谁加副本？半夜低谷谁缩回来省钱？

你可以自己写脚本解决其中一两个。但所有公司最终都会写出同一套东西——Google 把它十几年的内部经验（Borg 系统）开源成了 K8s。K8s 就是这四个问题的标准化答案。

K8s 具体干什么：用你的话翻译

K8s 的接口是声明式的（见第 00 章）。感受一下这个「翻译」过程：

你说（期望状态）K8s 做（持续维持）
「跑 3 份，一直活着」Deployment / ReplicaSet 的控制循环盯着副本数，少了补、多了删
「流量均匀分给这 3 份」Service 按标签选中它们，维护负载均衡规则
「后端之间能互相访问，但外部不行」NetworkPolicy 按标签设防火墙
「给我 20G 磁盘，别因重启丢数据」PVC 申请持久卷，跟着 Pod 挂载
「这个服务有 GPU 的机器才配跑」节点标签 + 节点选择器 / 亲和性
「这台机器在维护，别往上面放」污点（Taint）+ 容忍（Toleration）
「CPU 超过 70% 就加副本」HPA 自动扩缩容

注意右列的动词都是持续性的：盯着、维护、跟着。这不是「执行一次命令」，而是「维持一个状态」——第 00 章的模型一。

和 Docker 是什么关系

这是被问得最多、也答得最乱的一个问题。先看分层：

  • 镜像格式是 Docker 确立的 OCI 标准——K8s 直接沿用，你今天 docker build 出来的镜像，K8s 拿来就能跑
  • 容器运行时负责真正跑容器：containerd、CRI-O 等。K8s 通过 CRI（Container Runtime Interface）调用它们
  • K8s 在更上一层：决定容器跑在哪、跑几份、坏了怎么办

「K8s 移除 Docker 支持」的真相

早期 K8s 通过一个叫 DockerShim 的适配层直接调用 Docker daemon。但 Docker 是个面向开发者的全家桶（CLI、compose、build、daemon……），K8s 只需要其中「跑容器」那一小块。

于是 K8s 定义了 CRI 标准接口，让运行时各凭本事接入。DockerShim 在 1.20 标记废弃、1.24 移除。被移除的是适配层，不是兼容性：Docker 造的镜像照跑，Docker 作为开发工具照用。媒体标题党了。

那 Docker Compose 呢

Compose 也是声明式（一个 YAML 描述多个容器），但它是单机的：没有跨机器调度，没有控制循环自愈（容器退出就是退出了），没有集群级服务发现。

一个粗糙但准确的类比：Compose 是单台机器上的容器清单，K8s 是一个机群的操作系统。

什么场景该用，什么场景不该用

这一节比功能介绍更值钱，因为大部分 K8s 的痛苦来自误用。

适合用

  • 服务数量多（微服务），需要统一的部署、扩缩、观测方式
  • 流量有波动，需要弹性伸缩
  • 对可用性有要求，需要故障自愈、滚动升级不中断
  • 多团队协作，需要资源隔离与配额管理

不适合用

  • 单机就能扛住：一个 monolith + 一个数据库。docker compose 或干脆 systemd 就够了
  • 团队没有运维能力：K8s 本身是一个需要被运维的复杂系统。没有专人，它会成为你最大的故障源
  • 批处理 / 大数据为主：有更对口的调度器（YARN、Spark 自带调度），K8s 上跑只是「可以」，不是「合适」
一句话判断

K8s 解决的是规模带来的问题。如果你的规模没到，引入 K8s 等于引入它自身的全部复杂度，却用不上它的任何好处。

面试官视角

Q1：用一句话介绍 Kubernetes？

✕ 平庸答案 · 背定义

「K8s 是一个开源的容器编排平台，支持自动化部署、扩展和管理容器化应用。」

——官方定义的复述，零信息量，面试官无法判断你是否理解。

✓ 加分答案 · 从问题出发

「K8s 本质上是在回答一个问题：当容器多到单机管不过来时，怎么在一群机器上统一管理它们。它给出四个答案——调度解决『放哪』，Service 解决『怎么找到』，控制循环解决『坏了怎么办』，自动扩缩解决『流量变了怎么办』。而贯穿这四个答案的设计是声明式 API：你描述期望状态，系统持续维持它。」

Q2：K8s 和 Docker 的区别 / 关系？

✕ 平庸答案

「Docker 是容器技术，K8s 是管理容器的。」

方向对，但经不起追问：那 K8s 移除 Docker 支持是怎么回事？

✓ 加分答案 · 分层 + 历史

「它们是不同层的东西。Docker 确立了镜像的 OCI 标准，也提供运行时；K8s 是编排层，通过 CRI 标准接口调用运行时，不绑定任何具体实现。所谓『K8s 移除 Docker 支持』移除的是 DockerShim 这个适配层——因为 K8s 只需要『跑容器』这一小块能力，而 Docker daemon 是个面向开发者的全家桶。镜像格式完全兼容，Docker build 的镜像 K8s 照跑。」

常见误区

误区一：K8s 是 Docker 的升级版 / 替代品

不同层。Docker 解决「打包和单机运行」，K8s 解决「机群管理」。你的开发机上依然装 Docker，集群里跑的是 containerd。

误区二：上 K8s = 云原生 = 技术先进

工具匹配规模才有价值。三个服务的团队上 K8s，通常结果是：应用没变好，运维复杂度翻十倍，还多了一个需要半夜爬起来修的系统。

误区三：K8s 会「运行」我的容器

K8s 控制平面不碰任何容器。真正跑容器的是每个节点上的容器运行时，kubelet 只是它的调用者。控制平面挂了的集群里，已运行的容器可以继续跑很久——这个事实后面还会反复出现。

误区四：K8s 只能跑容器

K8s 调度的基本单位是 Pod，容器是其中最主要的负载，但不是唯一。通过扩展（如 KubeVirt）它也能管理虚拟机。理解成「容器编排」是对的，但要知道边界比这宽一点。
