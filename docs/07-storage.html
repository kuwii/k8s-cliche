存储

容器的磁盘随容器消亡。PV/PVC 把「谁要存储」和「谁提供存储」拆开。

一句话答案

三层模型：PV 是存储资源本体（供给侧），PVC 是用户的申请单（需求侧），StorageClass 是「如何动态创建 PV」的配方。

Pod 只认 PVC，不认 PV——和代码只依赖接口不依赖实现是一个道理。

问题：容器文件系统是临时的

容器内的写入存在于可写层，容器删除即消失；Pod 重建（换节点）更是什么都不剩。数据库、上传文件、日志归档都需要独立于容器生命周期的存储。

三层模型

  • PersistentVolume：管理员预先创建、或由 provisioner 动态创建的存储资源。是对一块真实存储（云盘、NFS、Ceph）的抽象
  • PersistentVolumeClaim：用户声明「我要多大、什么访问模式」。控制器拿它去匹配或创建 PV，完成 绑定（Bound）
  • StorageClass：描述「用什么 provisioner、什么参数创建 PV」。PVC 指定它，就能按需自动创建 PV，无需管理员预先铺盘

Pod 里这样用：

spec:
  containers:
    - name: db
      volumeMounts:
        - name: data
          mountPath: /var/lib/mysql
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: mysql-data   # 只引用 PVC，不关心背后是什么盘

访问模式与回收策略

概念取值含义
访问模式
（accessModes）		ReadWriteOnce（RWO）可被单个节点读写（最常用；云盘通常如此）
ReadOnlyMany（ROX）多节点只读
ReadWriteMany（RWX）多节点读写（需要 NFS/Ceph 等共享存储支持）
ReadWriteOncePod全集群仅单个 Pod 可挂载（比 RWO 更严）
回收策略
（reclaimPolicy）		RetainPVC 删除后 PV 保留，数据还在，需人工清理
DeletePVC 删除后连带删除底层存储——数据随之消失
Delete 策略 = 删 PVC 即删数据

动态供给的 StorageClass 默认多为 Delete。误删一个 PVC，数据库文件就没了。生产环境要么改 Retain，要么确保备份独立于 PVC 生命周期。

volume 类型对照

类型生命周期用途
emptyDir与 Pod 同生共死同 Pod 内容器共享的暂存区、缓存
hostPath绑定在特定节点仅 DaemonSet 类场景；Pod 漂移到别节点数据就「丢」了
persistentVolumeClaim独立于 Pod需要持久化的数据的标准答案
configMap / secret跟随源对象更新把配置/密钥以文件形式注入（见第 08 章）

CSI 一句话

CSI（Container Storage Interface）是存储厂商接入 K8s 的标准插件接口——和 CRI 之于运行时、CNI 之于网络同构。云厂商/开源存储实现 CSI 驱动，K8s 就能「认识」它的盘。

与 StatefulSet 的配合

volumeClaimTemplates 让每个副本自动获得专属 PVC：data-web-0、data-web-1……Pod 重建后按名字挂回自己那块盘。这是「稳定存储」保证的实现方式（第 05 章）。

面试官视角

Q：PV、PVC、StorageClass 的关系？

✕ 平庸答案

「PV 是存储，PVC 是申请，StorageClass 是分类。」

——「分类」是错的方向：StorageClass 不是 PV 的分类标签，而是创建配方。

✓ 加分答案

「PV 和 PVC 是供需两侧：PVC 是申请单，PV 是资源本体，两者绑定后 Pod 经 PVC 使用存储，不直接接触 PV。StorageClass 描述如何动态创建 PV——指定 provisioner 和参数——PVC 引用它就能按需自动开盘，免去管理员预铺。另外两个关键属性：访问模式决定能挂几个节点，回收策略决定 PVC 删除后数据去留，Delete 策略下删 PVC 就是删数据。」

常见误区

误区一：PVC 绑定成功 = 数据安全

绑定只说明盘挂上了。回收策略为 Delete 时，删 PVC 数据即消失。备份是另一件事。

误区二：RWO 的盘可以挂给多个 Pod

RWO 限制在单节点挂载。跨节点的第二个 Pod 会挂载失败；同节点多 Pod 共享 RWO 在某些实现下可行但属灰色地带，正解是 RWX 存储或拆分。

误区三：hostPath 是持久化方案

它把数据绑死在节点上：Pod 被调度到别节点就「丢」数据，节点磁盘故障即数据故障。除 DaemonSet 类场景外不要用。
