架构总览

两句话的架构：控制平面做决定，节点干活，中间只隔一个 API Server。

一句话答案

K8s 集群 = 控制平面（Control Plane） + 若干节点（Node）。控制平面负责决策与记账（apiserver / etcd / scheduler / controller-manager），节点负责真正跑容器（kubelet / kube-proxy / 容器运行时）。

记住每个组件「干什么」和「挂了会怎样」，架构题就再也问不倒你。

先看总图

图里只有两类盒子：做决定的（控制平面）和干活的（节点）。下面逐个过。

控制平面：做决定的四个组件

kube-apiserver —— 唯一入口

所有读写集群状态的请求都经过它：kubectl、kubelet、scheduler、controller-manager，无一例外。它做三件事：认证（你是谁）、鉴权（你允许吗）、准入（合规吗），然后才把请求落库或返回。

它是无状态的——状态都在 etcd——所以可以水平扩展，多副本前面挂负载均衡。

它是唯一能读写 etcd 的组件。这不是限制，而是设计：写入口单一，认证、审计、watch 通知才有统一的抓手。

etcd —— 唯一真相来源

一个分布式键值存储（基于 Raft 共识算法）。集群里所有资源对象——每个 Pod、每个 Service、每条 RBAC 规则——都以 JSON 形式存在这里。

注意它存的是声明的数据（spec 与 status 的记录），不是容器本身。容器跑在各节点的运行时里，etcd 里只有「账本」。

它是整个集群最金贵的组件：etcd 数据丢了，集群就失忆了。所以生产环境必须多副本 + 定期备份。

kube-scheduler —— 只写答案，不动手

监听「还没分配节点的 Pod」，为它选一个节点，然后把 nodeName 写回 API Server。完事。

选择过程两阶段：过滤（Filter）——剔除不满足条件的节点（资源不够、污点不容忍）；打分（Score）——给剩下的节点排序，选最优。

关键认知：scheduler 不启动任何东西。它只做一个绑定（bind）动作。真正拉起容器的是节点上的 kubelet——两者从头到尾没有直接通信（第 00 章模型四的例子）。

kube-controller-manager —— 控制循环的集合体

第 00 章说「每个控制器都是一个调谐循环」。这个进程里跑着几十个内置控制器：

  • Deployment / ReplicaSet 控制器：维持副本数
  • Node 控制器：盯着节点心跳，节点失联就标记、驱逐其上的 Pod
  • EndpointSlice 控制器：按标签维护 Service 的后端列表
  • ServiceAccount / Namespace / Job 控制器……

它是「自愈」二字的物理载体。它挂了，集群不会立刻死，但从此没人修任何东西。

节点：干活的三件套

kubelet —— 节点上的代理人

每个节点一个。它监听「分配给本节点的 Pod」，然后：

  • 通过 CRI 让容器运行时拉镜像、起容器
  • 通过 CNI 给 Pod 配网络，通过 CSI 挂存储卷
  • 执行探针（liveness / readiness / startup），按要求重启容器
  • 把 Pod 与节点的状态写回 API Server

kubelet 是控制平面意志在节点上的执行者，也是节点现实向控制平面的汇报者。双向的。

kube-proxy —— 名字最有欺骗性的组件

它维护 Service 的转发规则（iptables 或 IPVS 模式）。注意：在主流模式下，它不在数据路径上。

规则写进内核之后，流量由内核的 netfilter 直接转发，kube-proxy 进程本身一个包都不碰。它是个「规则维护员」，不是「代理」。叫这个名字是历史遗留。

容器运行时 —— 真正跑容器的

containerd、CRI-O 等，实现 CRI 接口。拉镜像、创建隔离环境、启动进程——所有「真正发生」的事都在这一层。K8s 控制平面从头到尾不碰容器（第 01 章误区三）。

附加组件：不是内置的，但几乎是必需的

下面这些不属于 K8s 二进制，而是以工作负载形式部署在集群里的「插件」。面试时区分清楚很加分：

组件职责形态
CoreDNS集群内 DNS：把 Service 名解析成 ClusterIPDeployment（跑在集群里）
CNI 插件（Calico / Cilium / Flannel…）给 Pod 分配 IP、实现跨节点网络、NetworkPolicyDaemonSet + 节点上的二进制
Ingress 控制器（nginx / traefik…）七层路由：域名 / 路径 → ServiceDeployment + LoadBalancer Service
metrics-server聚合资源指标，喂给 HPA 和 kubectl topDeployment

有个有趣的自指：CoreDNS 本身跑在集群里、是个 Pod——集群的基础设施由集群自己承载。这也是为什么新集群装好后第一件事往往是装 CNI：在 CNI 就绪前，CoreDNS 的 Pod 会一直卡着。

每个组件「挂了会怎样」

这张表是架构理解的试金石。能背出职责是及格，能说清故障影响才是理解。

组件挂了之后
kube-apiserver一切新变更停摆：kubectl 无响应、新 Pod 无法创建。但已运行的工作负载继续跑——数据路径不依赖它
etcd最严重。集群失忆：apiserver 无数据可读，等同全集群不可用。多副本 + 备份是唯一解
scheduler新 Pod 永远 Pending；已运行的 Pod 不受影响
controller-manager没有自愈、没有扩缩、没有副本维持。删一个 Pod 就少一个，没人补。集群进入「僵尸模式」：活着，但不再自我修复
kubelet（单节点）该节点失联被标记 NotReady；宽限期后其上的 Pod 被控制器在别处重建。节点上已跑的容器可能还在，但集群已经「不认」它了
kube-proxy（单节点）该节点的 Service 规则不再更新：新 Service 不通；旧规则还在内核里，存量连接大多照常
CoreDNS集群内域名解析失败：应用间用服务名互访全部报错。用 IP 直连的侥幸存活
一个贯穿全表的规律

控制平面的故障影响「未来的变更」，节点数据路径的故障影响「当前的流量」。两者解耦（第 00 章模型四）的直接红利就是：大脑短暂罢工，四肢还能继续动。

面试官视角

Q1：介绍一下 K8s 的架构？

✕ 平庸答案 · 报菜名

「控制平面有 apiserver、etcd、scheduler、controller-manager；节点有 kubelet、kube-proxy、容器运行时。」

——正确但扁平，像目录页。面试官追问「它们怎么协作」就露馅。

✓ 加分答案 · 按「决策 / 执行」组织，带协作关系

「我习惯把架构分成决策和执行两层。决策层是控制平面：apiserver 是唯一入口和唯一能写 etcd 的组件，etcd 存所有资源对象，scheduler 负责选节点，controller-manager 里跑着所有内置控制循环。执行层是节点：kubelet 接收指令、调用运行时跑容器，并把状态写回去。

两层之间只通过 API Server 通信，组件彼此不直接调用——scheduler 选完节点只是写回一个字段，kubelet 靠 watch 发现自己有活干。这个设计的好处是故障隔离：控制平面挂了，已运行的负载和数据路径还能继续工作一段时间。」

Q2：kube-proxy 是怎么转发流量的？

✕ 平庸答案（且是错的）

「kube-proxy 把发给 Service 的流量代理到后端 Pod。」

——「代理」二字是陷阱。追问「数据路径经过 kube-proxy 进程吗」就崩了。

✓ 加分答案 · 区分控制路径与数据路径

「严格说它不转发。kube-proxy 监听 Service 和 EndpointSlice 的变化，把转发规则写进内核——iptables 模式写 netfilter 规则，IPVS 模式写 IPVS 表。之后流量由内核直接转发，kube-proxy 不在数据路径上。所以它是个规则维护员，叫 proxy 是历史遗留。这也解释了为什么 kube-proxy 挂了之后存量连接大多不受影响：规则还在内核里。」

常见误区

误区一：kube-proxy 在转发 Service 流量

见上。它维护内核规则，数据路径不经过它。这是架构题里最高频的陷阱。

误区二：etcd 里存着容器的状态

etcd 存的是资源对象的声明与状态记录（JSON）。容器的真实运行状态在各节点运行时里，kubelet 观察后写回 status。账本和货物是两回事。

误区三：master 是一台机器

「master」是旧称，现在叫控制平面，而且生产环境通常是多副本高可用：多个 apiserver 实例 + 奇数个 etcd 成员（Raft 需要多数派）。把控制平面理解成单点，HA 方案就想不明白。

误区四：控制平面挂了，服务立刻全死

不会。已运行容器、已写入内核的网络规则都还能工作。死的是「变更能力」：不能部署、不能自愈、不能扩缩。理解这个时间差，故障预案才写得对。
