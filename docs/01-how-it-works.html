主线 · 第 01 章

工作原理

在记住任何 YAML 之前，先记住这四条。

一句话答案

Kubernetes 的全部设计建立在四个思想之上：声明式 + 控制循环、一切皆资源、标签解耦、中心辐射架构。

理解了这四条，K8s 里绝大多数对象和行为你都能自己推导出来，不需要背。

为什么需要这一章

K8s 的学习曲线陡峭，但陡峭的地方往往不在「难」，而在「反直觉」。

很多人学 K8s 的方式是逐个背对象：Pod 是什么、Service 是什么、Deployment 是什么……背到第十个就崩了，因为对象之间有微妙的关联，而死记硬背抓不住这些关联。

📖 名词提示 · Pod

K8s 的最小调度单位：一组共享网络与存储的容器。你说「跑 3 个副本」，在 K8s 里就是「维持 3 个 Pod」——后文一切都以 Pod 为基本单位谈（03 · 一个 Pod 的诞生 细说）。

真实情况是：K8s 的核心概念很少，对象很多。对象只是同一套思想在不同场景下的具体化。所以正确的顺序是先拿到思想，再去认对象——那时候你会发现它们长得都很像。

模型一

声明式 + 控制循环

你描述期望，系统持续地让现实逼近期望。这是「自愈」的来源，是 K8s 的灵魂。

模型二

一切皆资源

所有东西都是带 spec / status 的 API 对象，用统一的 REST API 读写。

模型三

标签与选择器

对象之间没有从属关系，只有标签匹配。松耦合带来极强的灵活性。

模型四

中心辐射架构

组件彼此不直接通信，只围着 API Server 转，靠「监听」协作。

模型一：声明式 + 控制循环

这是 K8s 的灵魂。

命令式 vs 声明式

命令式（Imperative）：你告诉系统每一步怎么做。

# 启动三个实例
docker run -d myapp
docker run -d myapp
docker run -d myapp

声明式（Declarative）：你告诉系统你想要什么结果，怎么达成是系统的事。

# 我要三个实例
spec:
  replicas: 3

区别不只在写法。命令式的语句执行完就结束了——如果之后有一个实例挂了，没有任何东西会去补上。而声明式描述的是一个持续成立的状态，系统会一直努力让它成立。

这就是 K8s「自愈」能力的来源。它不是某个特殊功能，而是声明式的必然结果。

控制循环（Control Loop）

声明式要生效，需要一个东西不停地干活，这就是控制循环，也叫调谐循环（Reconcile Loop）：

用伪代码表达，K8s 里每一个控制器（Controller）本质上都是这个循环：

for {
    desired := getDesiredState()    // 从 API Server 读 spec
    current := getCurrentState()    // 观察集群实际情况
    diff := desired - current       // 求差
    applyChanges(diff)              // 让 current 趋向 desired
}

举例：ReplicaSet 控制器不断检查「期望 3 个副本，实际几个」。少了就创建，多了就删除。它不关心为什么少了——可能是节点宕机、可能是你手动删了、可能是探针失败被重启——它只关心差异，然后消除差异。

📖 名词提示 · ReplicaSet

Deployment 和 Pod 之间的执行层：Deployment 说「要 3 个」，ReplicaSet 负责让实际数量始终是 3。先记住它存在即可（05 · 工作负载 细说）。

这解释了什么

一旦接受这个模型，很多现象就不需要单独记忆了：

现象解释
kubectl delete pod 之后 Pod 又回来了实际状态偏离了期望状态，控制器消除了差异
不该手动去改 Pod你改的是「实际状态」，控制器会把它调谐回去
应该改 Deployment 而不是改 Pod要改的是「期望状态」
节点挂了，上面的 Pod 自动跑到别处控制器发现副本数不足，补上了
📖 名词提示 · kubectl

K8s 的命令行客户端：你敲的每条命令，本质都是发给 API Server 的 HTTP 请求。它本身不理解调度、不理解容器（12 · 运维与排障 细说）。

一个重要的推论：最终一致

最终一致（Eventually Consistent）

控制循环是持续逼近而非一次性完成的。你 kubectl apply 一个 YAML，命令返回成功只代表「API Server 收下了这份期望状态」，不代表它已经生效。中间要经历调度、拉镜像、启动容器等一系列异步过程。

这也是为什么 K8s 里到处是「等待就绪」的机制（比如探针），以及为什么 apply 之后立刻查状态，常常看到的不是最终结果。

模型二：一切皆资源

K8s 可以被理解为：一个分布式的键值存储，加上一群不断调谐它的控制器。

所有东西——Pod、Service、Node、乃至权限规则——都被抽象成资源（Resource），也叫 API 对象（API Object），通过统一的 REST API 读写。

统一的骨架

几乎每个 K8s 对象都长这样：

apiVersion: apps/v1      # 属于哪个 API 组、哪个版本
kind: Deployment         # 是什么类型
metadata:                # 元信息：名字、命名空间、标签……
  name: web
  namespace: default
  labels:
    app: web
spec:                    # ★ 期望状态：你想让它变成什么样（你写）
  replicas: 3
status:                  # ★ 实际状态：它现在实际是什么样（K8s 写）
  readyReplicas: 2
spec 与 status 的分离是理解 K8s 的关键
  • spec 由你（或 Helm、控制器）写入，描述期望
  • status 由 K8s 组件写入，描述现实
  • 控制循环做的事，就是让 status 不断逼近 spec

回头看模型一，会发现它就是这里的机制实现。两个模型是咬合的。

📌 实用推论：排查问题时，kubectl get xxx -o yaml 里先看 status。期望与现实的差距，往往直接写在那里。

这解释了什么

现象解释
kubectl 能用同一套语法操作所有资源它们都是 REST 资源，动词一致
kubectl api-resources 能列出所有类型类型本身就是 API 的一部分
CRD 能无缝扩展 K8s只是往 API 里注册一种新资源，其余机制自动复用
一切都可以用 YAML 描述和版本管理因为一切都是数据

最后一条很重要，它意味着 K8s 集群的完整状态可以被 Git 管理——这就是 GitOps 的全部前提。

模型三：标签与选择器

这是 K8s 最反直觉、也最灵活的一处设计。

没有从属关系，只有匹配关系

按常理，你会以为 Service 和它转发的 Pod 之间存在某种「包含」或「绑定」关系。并没有。

Service 只声明一个选择器（Selector）：

# Service
spec:
  selector:
    app: web        # 我负责所有带这个标签的 Pod
# Pod
metadata:
  labels:
    app: web        # 我带这个标签

两者互不知晓对方存在。Service 不「持有」Pod 列表，它只是持续地按标签筛选，筛出什么就把流量转给什么。

这种松耦合带来了极强的灵活性：

  • Pod 可以随时销毁重建、IP 不断变化，Service 完全不用改
  • 想切流量，只要改 Pod 的标签，或者改 Service 的选择器
  • 灰度发布、蓝绿部署，本质上都是在操纵标签匹配关系

无处不在

标签选择器不是 Service 的专属功能，而是 K8s 的通用组织方式：

场景谁在选择谁
Deployment 管理 Pod通过 ReplicaSet 的标签选择器
Service 转发流量选择器匹配 Pod 标签
调度亲和性节点选择器 / 节点亲和性匹配节点标签
NetworkPolicy选择器决定策略作用于哪些 Pod
kubectl get pods -l app=web你在选择 Pod

注意最后两行：标签不只打在 Pod 上，节点也有标签。同一套机制。

这解释了什么

现象解释
手动建一个带相同标签的 Pod，Service 会自动把流量打给它匹配上了就纳入
删掉 Service 的 Pod 却「删不干净」Deployment 的选择器还在匹配，会重建
Service 后面没有可用 Pod 时不报错，只是超时选择结果为空，这是合法状态
最常见的坑

Service 不通，八成是 selector 和 Pod 的 labels 没对上。用 kubectl get endpoints 一看便知——如果是空的，就是标签没匹配上。

模型四：中心辐射架构

前三条讲的是「怎么想」，这一条讲「怎么搭」。

只有 API Server 能碰 etcd

K8s 的所有组件——调度器、各种控制器、kubelet、kubectl——彼此之间不直接通信。它们只和 API Server 说话。

📖 名词提示 · API Server / etcd

API Server：K8s 唯一的入口，所有组件（包括你）只和它通信。etcd：分布式键值存储，集群状态的唯一真相来源，而能读写它的只有 API Server。两者是 02 · 架构总览 的主角。

组件靠「监听」协作

组件之间既然不直接通信，那怎么协作？答案是：监听资源变化（Watch）。

以「调度一个 Pod」为例：

  1. API Server 把 Pod 写入 etcd，此时它的 spec.nodeName 为空
  2. 调度器一直监听着「未指定节点的 Pod」，发现了一个
  3. 调度器算出该放哪个节点，把结果写回 API Server（给 Pod 填上 nodeName）
  4. 目标节点的 kubelet 一直监听着「nodeName 是我的 Pod」，发现有活了
  5. kubelet 拉起容器

注意整个过程：调度器和 kubelet 从头到尾没有说过一句话。它们只是各自盯着 API Server 上自己关心的那部分数据，看到变化就干活。

这是彻底的解耦。（这条链路的完整版本，就是第 03 章 · 一个 Pod 的诞生。）

这解释了什么

现象解释
API Server 可以水平扩展，加实例就行它无状态，状态都在 etcd
调度器挂了，已运行的 Pod 不受影响组件之间没有直接依赖
网络分区时节点上的 Pod 还能继续跑kubelet 与 API Server 断连不会立刻杀 Pod
想加个新功能，不用改现有组件新写个控制器监听相关资源即可（这就是 Operator 的原理）
etcd 必须做高可用，它挂了很麻烦它是唯一的真相来源

四条模型怎么咬合

它们不是并列的四条，而是一个整体：

  • 因为一切皆资源，所以状态可以被统一读写 →
  • 因为状态可读写，所以可以用 spec 表达期望、status 记录现实，用控制循环去逼近 →
  • 因为控制循环只需要「读状态、写状态」，所以组件之间不必直接通信，围着 API Server 转就行 →
  • 而资源之间如何关联，靠的是标签匹配，而不是硬编码的引用关系

这套组合拳的结果，就是一个高度解耦、可自愈、可无限扩展的系统。

面试官视角

Q：说说你对 Kubernetes 设计理念的理解？

这是道开放题，考的是你有没有体系，而不是你背了多少名词。

✕ 平庸答案 · 罗列组件

「K8s 有 apiserver、etcd、scheduler、kubelet……」

这只是背了架构图，没有观点。面试官听完不知道你到底理解不理解。

✓ 加分答案 · 抓住声明式这个核心，再展开

「K8s 最核心的设计是声明式 API 加控制循环。用户描述期望状态写在 spec 里，各个控制器通过调谐循环不断让实际的 status 逼近它。所谓自愈能力，本质上就是这个循环的自然结果，而不是某个独立特性。

支撑这个理念的是两点：一是一切皆资源，所有对象都通过统一的 API 读写，spec 和 status 严格分离；二是中心辐射架构，组件之间不直接通信，只监听 API Server 上的资源变化，因此彼此解耦，可以独立扩展和替换。

这套设计也带来了可扩展性——写一个自定义控制器监听自定义资源，就是 Operator 模式，它复用的是和内置控制器完全相同的机制。」

这段话里没有一个多余的名词，但把架构、自愈、扩展性都串起来了。

常见误区

误区一：「声明式」=「YAML 写法」

不是。命令式也能写 YAML（kubectl apply 和 kubectl run 的区别不在格式）。声明式的本质是你描述的是一个需要持续维持的状态，而非一次性的动作。

误区二：控制器会「知道」发生了什么

不会。控制器只看到「期望 3 个，实际 2 个」，它不知道也不关心为什么少了。这种「无知」恰恰是它健壮的原因——不管什么原因导致的偏差，处理方式都一样。

误区三：kubectl apply 成功 = 部署成功

不是。apply 成功只意味着 API Server 接受了你的期望状态。后续调度、拉镜像、启动全是异步的，可能失败。要确认真的起来了，得看 kubectl rollout status 或 Pod 的 status。

误区四：Service 里存着 Pod 列表

Service 对象本身不存 Pod 列表，它只存选择器。真正维护后端列表的是 EndpointSlice（旧版本是 Endpoints）资源，由控制器根据标签匹配自动生成和更新。
