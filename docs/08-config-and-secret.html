配置与密钥

配置进镜像是反模式。ConfigMap 与 Secret 把「环境差异」从镜像里剥出来。

一句话答案

ConfigMap 存明文配置，Secret 存敏感信息（base64 编码，默认不是加密）。注入容器有三种方式：环境变量、envFrom 批量、volume 挂载——三者热更新行为不同，这是本章唯一的重点。

为什么配置要外置

同一个镜像要跑在 dev / staging / prod 三个环境，差异只有数据库地址、开关、密钥。配置写死在镜像里 = 每个环境build一个镜像 = 环境不一致的灾难。外置后：镜像不变，配置随环境换。

三种注入方式与热更新

方式写法ConfigMap 更新后
环境变量（单键）env.valueFrom.configMapKeyRef不生效，需重启容器
envFrom（整包）envFrom.configMapRef不生效，需重启容器
volume 挂载volumes.configMap自动更新（kubelet 同步周期，约一分钟量级延迟）

原因很直白：环境变量在容器创建时就固化了，进程不改它就不会变；而 volume 是 kubelet 持续同步的文件。

subPath 陷阱

用 subPath 挂载 ConfigMap 的单个键为文件时，不会自动更新——自动更新只对整个 ConfigMap 目录挂载成立。这是生产上「配置改了不生效」的经典原因之一。

应用侧要真正「热加载」，还需要自己监听文件变化或提供 reload 接口；K8s 只保证文件会变。

Secret：编码 ≠ 加密

apiVersion: v1
kind: Secret
metadata:
  name: db-cred
type: Opaque            # 通用类型
data:                   # 注意是 data（base64），不是 stringData
  password: cGFzc3dvcmQxMjM=   # "password123" 的 base64
  • base64 是编码，任何人可解。它存在的意义是避免二进制/特殊字符问题，不是保密
  • 真保密需要：etcd 静态加密（EncryptionConfiguration，集群级配置）+ RBAC 限制 Secret 读权限 + 传输 TLS
  • 常见类型：Opaque（通用）、kubernetes.io/tls（Ingress 证书）、kubernetes.io/dockerconfigjson（镜像仓库凭证）
  • 更高要求的团队会用外部密钥系统（Vault、External Secrets Operator）：Secret 只是同步进来的投影

两个实用补充

  • downwardAPI：把 Pod 自己的元数据（名字、namespace、标签、资源 limits）注入环境变量或文件——容器「认识自己」的方式
  • immutable 字段：ConfigMap/Secret 设 immutable: true 后不可修改，只能删建。换来的是 kubelet 不再轮询它，大规模集群下显著降低 apiserver 压力；更新靠改引用名（配合 Deployment 换模板触发滚动）

面试官视角

Q：ConfigMap 更新后应用怎么感知？

✕ 平庸答案

「更新 ConfigMap 就生效了。」

——只对 volume 挂载成立，且漏了延迟与 subPath 例外；环境变量方式完全不生效。

✓ 加分答案

「分注入方式。环境变量和 envFrom 在容器创建时固化，更新 ConfigMap 不会生效，必须重启容器——通常用改注解触发滚动更新的做法。volume 挂载由 kubelet 持续同步，约一分钟量级延迟后文件变化，但 subPath 单键挂载例外，它不更新。最后还要应用自己支持热加载，K8s 只保证文件会变。」

常见误区

误区一：Secret 是加密存储的

默认只是 base64 编码，etcd 里明文可解（除非集群开了静态加密）。把 Secret 当加密方案是安全事故的起点。

误区二：配置改了应用立刻用上

见上表：环境变量方式根本不更新；volume 方式有同步延迟；应用还要自己 reload。

误区三：ConfigMap 可以存大文件随便用

单个 ConfigMap/Secret 上限 1MB（etcd 单值限制的传导）。大配置应拆键、外置存储或走镜像。
