一个 Pod 的诞生

从你敲下 kubectl apply，到容器真正跑起来接流量——中间发生了什么。

一句话答案

一份 YAML 的旅程：kubectl → apiserver（三道关卡）→ etcd 落库 → scheduler 绑定节点 → 该节点 kubelet 接单 → CRI 拉镜像起容器（CNI 配网络）→ 探针通过 → 状态回写 → Service 发现它。

全程没有任何两个组件直接对话。它们只是轮流读写 API Server 上的同一份记录。这一章是第 00 章四条模型的同一次演出。

为什么这一章是主轴

前面三章给了你思想和零件。这一章把零件装起来跑一遍。

这条链路穿过了几乎所有核心组件，也解释了几乎所有常见故障现象：Pending、ContainerCreating、ImagePullBackOff、CrashLoopBackOff、Ready 0/1——每一个都是旅程在某一站卡住了。读懂旅程，故障排查就从「背现象」变成「查站点」。

出发之前：你提交的到底是什么

kubectl apply -f deployment.yaml 时，kubectl 做的事很简单：读 YAML，把它转换成一次对 API Server 的 REST 请求。

YAML 只是序列化格式。真正被提交的是一个 API 对象（第 00 章模型二）：带 apiVersion / kind / metadata / spec 的结构化数据。kubectl 本身不理解调度、不理解容器——它只是个 HTTP 客户端。

顺带解开一个常见困惑

apply 与 create 的区别不在「格式」而在语义：create 是「新建这个对象」，已存在就报错；apply 是「让集群状态等于这份声明」，存在则更新。后者才是声明式的用法，也是 GitOps 的基础动作。

旅程的九个站点

① 三道关卡：认证 → 鉴权 → 准入

请求到达 API Server，先过三关：

  • 认证（Authentication）：你是谁？证书、Token、ServiceAccount……
  • 鉴权（Authorization）：你被允许做这个动作吗？RBAC 规则在这里生效
  • 准入（Admission）：这个请求合规吗？分两阶段——mutating（可以改写请求，比如注入默认值、sidecar）在前，validating（只判断接受或拒绝）在后

面试常追问顺序：mutating 必须在 validating 之前——先改完再校验，校验的才是最终形态。

② 落库：Pod 诞生，但还只是个账本条目

过了三关，对象被写入 etcd。此刻 Pod「存在」了——但只存在于账本里：没有节点、没有容器、没有 IP。

它的状态是 Pending，spec.nodeName 为空。如果你这时 kubectl get pod，看到的就是这一站。

③ 调度器接单：过滤 → 打分 → 绑定

scheduler 一直 watch 着「nodeName 为空的 Pod」。发现新 Pod 后：

  1. 过滤（Filter）：剔除不满足条件的节点——资源不够、污点不容忍、节点选择器不匹配
  2. 打分（Score）：给候选节点排序——资源均衡、亲和性偏好等
  3. 绑定（Bind）：把选中的节点写回 Pod 的 spec.nodeName
关键认知

scheduler 到此就下班了。它没有启动任何东西，只是写了一个字段。「调度」在 K8s 里的全部含义就是这一次绑定。

④ kubelet 接单：靠 watch，不靠通知

没有任何人「通知」kubelet。每个节点的 kubelet 都在 watch「nodeName 等于我的 Pod」。绑定写入的那一瞬，目标节点的 kubelet 看到了变化，把活领走。

这是第 00 章模型四的标准动作：协作 = 各自监听同一份数据。

⑤ CRI：拉镜像、建沙箱、起容器

kubelet 调用容器运行时（CRI 接口），运行时依次：

  1. 拉取镜像（不存在或拉不到，就卡在这里 → ImagePullBackOff）
  2. 创建 Pod 沙箱（sandbox）——Pod 的网络命名空间就在这时建立，CNI 插件在此给 Pod 分配 IP
  3. 按顺序启动 init 容器，再启动主容器

注意 IP 是沙箱创建时就有的，早于容器启动。Pod 的 IP 属于沙箱，容器共享它——这解释了「同 Pod 内容器共享网络」。

⑥ 探针上岗

容器跑起来后，kubelet 按声明执行探针：

  • startupProbe：允许慢启动，通过前其他探针不工作
  • livenessProbe：失败 → 重启容器（「它还活着吗」）
  • readinessProbe：失败 → 从 Service 后端摘除（「它能接客吗」）

两者区别是高频考点：liveness 管生死，readiness 管流量。readiness 失败不会重启容器，只会让它暂时不接流量。

⑦ 状态回写：Ready = true

kubelet 持续观察本机容器，把结果写回 API Server：容器状态、Pod IP、Ready 条件。到此，账本上的记录第一次与现实一致。

⑧ EndpointSlice 更新

EndpointSlice 控制器 watch 到「某个 Ready 的 Pod 匹配某 Service 的选择器」，把它的 IP:Port 加入该 Service 的后端列表。

下一跳开始，Service 的负载均衡规则里有了这个 Pod——它正式可以接客了。

⑨ 之后：永不停歇的循环

旅程没有终点。kubelet 继续汇报、探针继续探测、控制器继续调谐。Pod 的「一生」就是第 00 章那个循环的一次实例化。

复盘：看它走一遍

卡在哪一站 = 你看到什么

kubectl get pods 的每个异常状态，都是旅程在某一站卡住的别名：

你看到的卡住的站点常见原因
Pending③ 调度资源不足、污点不容忍、PVC 未绑定、没有满足选择器的节点
ContainerCreating⑤ 镜像 / 卷 / 网络镜像拉取中或失败、Secret 缺失、存储卷挂载失败、CNI 未就绪
ErrImagePull / ImagePullBackOff⑤ 拉镜像镜像名写错、无拉取权限、私有仓库未配 imagePullSecret
CrashLoopBackOff⑤ 之后容器启动进程立即退出：命令写错、缺配置、依赖连不上、OOM
Running 但 READY 0/1⑥⑦ readiness探针配置过苛、端口没监听、依赖服务未就绪
Terminating 卡住优雅终止阶段finalizer 未移除、进程不响应 SIGTERM
排查心法

先问「卡在哪一站」，再问「为什么」。kubectl describe pod 看事件（Events），kubectl logs 看容器输出——前者对应旅程的调度 / 拉取 / 挂载段，后者对应容器内部段。两张片子拍完，九成问题现形。

一个重要澄清：容器崩溃重启，不走这条旅程

容器崩了被重启，是 kubelet 与运行时的本地行为（依据 restartPolicy）：不经过 scheduler，不重新调度，IP 通常不变（沙箱还在）。

只有当 Pod 对象本身被重建——节点故障被驱逐、Deployment 滚动更新、被人 delete——才会重新走完整旅程，拿到全新的 IP 和（可能的）全新节点。

这个区分解释了为什么「Pod IP 会变」和「容器重启 IP 不变」可以同时为真。

面试官视角

Q：详细描述从 kubectl apply 到 Pod Ready 的完整流程。

这是架构类面试的压轴题，考的是能否把组件串成因果链。

✕ 平庸答案 · 组件流水账

「kubectl 发给 apiserver，存到 etcd，scheduler 调度到节点，kubelet 启动容器，然后就好了。」

——骨架对，但每个关节都是糊的：准入呢？绑定是什么意思？CNI 在哪一步？Ready 是谁写的？

✓ 加分答案 · 带关键机制的因果链

「分九步。kubectl 把 YAML 转成 REST 请求发给 apiserver；apiserver 依次做认证、鉴权、准入——准入里 mutating 在 validating 之前——通过后写入 etcd，此刻 Pod 诞生但 nodeName 为空，状态 Pending。

scheduler watch 到未绑定的 Pod，过滤、打分后把 nodeName 写回——注意它只做绑定，不启动任何东西。目标节点的 kubelet 靠 watch 发现自己有活，通过 CRI 让运行时拉镜像、创建 Pod 沙箱，CNI 在沙箱创建时分配 IP，然后启动 init 与主容器。

容器起来后探针开始工作；readiness 通过、kubelet 把 Ready 状态写回 apiserver；EndpointSlice 控制器随即把这个 Pod 加入 Service 后端，开始接流量。

整条链上没有任何两个组件直接通信，全部通过读写 API Server 上的共享记录协作——这也是为什么控制平面短暂故障时，已运行的 Pod 不受影响。」

常见误区

误区一：scheduler 负责启动容器

scheduler 只写 nodeName 一个字段。启动是 kubelet + 运行时的事。两者无直接通信。

误区二：kubectl apply 返回成功 = Pod 跑起来了

返回成功只代表通过了第 ① 站、完成了第 ② 站落库。后面七站全是异步的，任何一站都可能失败。确认要靠 kubectl rollout status 或观察 Ready。

误区三：kubelet 从 etcd 拉取自己的配置 / YAML

kubelet 只与 apiserver 通信（唯一入口原则）。它 watch 到的是 Pod 对象，不是 YAML 文件；YAML 只是你提交时的序列化形式。

误区四：容器每次重启都走完整调度流程

崩溃重启是 kubelet / 运行时依据 restartPolicy 的本地行为，不经过 scheduler。只有 Pod 对象被重建才重走全流程。

误区五：Service 访问不通，一定是 Service 配错了

高频真凶是 Pod 没 Ready：readiness 探针失败 → Pod 不进 EndpointSlice → Service 后端为空。先 kubectl get endpoints，再回头查探针。
