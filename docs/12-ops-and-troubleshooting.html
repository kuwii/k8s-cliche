运维与排障

排障不是背命令，是「先定位卡在哪一层，再取对应的证据」。

一句话答案

排障三板斧：describe 看事件、logs 看输出、get -o yaml 看期望与现实的差距。顺序通常是先事件后日志——因为日志可能根本不存在（容器没起来），而事件永远在说话。

方法论：先分层，再取证

拿到「服务不正常」，先问它属于哪一层：

  1. Pod 层：Pod 起不来 / 反复重启 / 不 Ready → 走第 03 章的卡站对照表
  2. 服务层：Pod 全 Ready 但访问不通 → Service / EndpointSlice / DNS / NetworkPolicy
  3. 节点层：单节点上的 Pod 集体异常 → 节点资源压力、kubelet、磁盘、NotReady
  4. 集群层：全局性异常 → 控制平面组件、etcd、证书过期

分层之后，取证手段是确定的：Pod 层看 events 和 logs；服务层看 endpoints 和规则；节点层看 describe node 和节点指标；集群层看组件日志与 kubectl get componentstatuses 类信号。

五个经典案例（一句话版）

  • 部署后 502：endpoints 为空 → Pod 的 readiness 探针端口写错 → 改探针，滚动更新
  • 间歇性超时：CPU limit 过低导致节流毛刺 → 提高或取消 CPU limit（第 09 章）
  • 配置改了不生效：注入方式是环境变量 → 触发滚动更新；或 volume 但用了 subPath
  • 节点加进来却不调度：节点带未容忍的污点（新节点 taint 未移除）→ 检查 taints
  • 集群证书过期全站 401：kubeadm 集群证书轮换未做 → 定期轮换是运维清单固定项

面试官视角

Q：一个 Pod 处于 CrashLoopBackOff，你怎么排查？

✕ 平庸答案

「看日志，找到报错修掉。」

——崩溃中的容器 kubectl logs 默认看不到输出（要看 -p）；也没体现分层思路。

✓ 加分答案 · 分层取证

「先 describe pod 看 Events 确认是容器退出导致的循环（退出码很关键：137 多为 OOM，1/2 多为应用自身）。然后 kubectl logs -p 看上一个实例的输出；如果完全没有输出，说明进程启动即死，查命令与入口点。OOM 怀疑则看 lastState.terminated.reason 与内存 limit。需要现场时用 kubectl debug 附加临时容器保留文件系统检查。整个过程是『事件定性质、日志定原因、现场定细节』。」

常见误区

误区一：排障先看日志

先看事件。容器没起来的 Pod 没有日志可看，而 Events 记录了调度、拉镜像、挂载、探针的每一步裁决。

误区二：kubectl logs 能看到崩溃容器的输出

默认看当前实例。崩溃重启中的要看 -p（previous）。不知道这个参数的人会在空输出前发呆。

误区三：删了重建能解决一切

它同时销毁了现场：事件、退出码、文件系统。先取证再动手；生产环境的「重启大法」应是被迫的最后手段。
