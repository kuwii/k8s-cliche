专题 · 第 10 章

安全

四层防线：你是谁、你能干什么、你的 Pod 能干什么、谁能和谁说话。

一句话答案

K8s 安全是四层：认证（证书 / Token / ServiceAccount）→ RBAC（谁能对什么资源做什么动作）→ Pod 安全（SecurityContext + Pod Security Admission）→ NetworkPolicy（Pod 间流量防火墙）。

最小权限原则贯穿四层：默认什么都别给，按需开。

第一层：认证（你是谁）

  • 客户端证书：kubeconfig 里那对 crt/key，人或组件的长期身份
  • ServiceAccount Token：Pod 的身份。现代方式是绑定投影卷（Bound Service Account Token）：带过期时间、按受众签发，比旧的全权限长期 token 安全得多
  • OIDC：对接企业 IdP（如 Dex、云厂商 IAM），kubectl 登录走浏览器

认证只回答「你是谁」，不回答「你能干什么」——后者是下一层。

第二层：RBAC（你能干什么）

  • Role / ClusterRole：规则集合，每条规则 = 资源（pods、deployments…）+ 动词（get/list/watch/create/update/patch/delete）
  • RoleBinding / ClusterRoleBinding：把规则集绑到主体（User / Group / ServiceAccount）
  • Role 作用于单个 namespace；ClusterRole 可集群级使用，也可通过 RoleBinding 「降级」用在某个 namespace
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: prod
  name: pod-reader
rules:
  - apiGroups: [""]          # 核心组
    resources: ["pods"]
    verbs: ["get", "list", "watch"]   # 只读，不能删

排错利器：kubectl auth can-i delete pods --as=system:serviceaccount:prod:my-sa —— 直接问「这个身份能不能做这件事」。

第三层：Pod 自身的安全姿态

Pod Security Admission（PSA）

namespace 级三档策略，取代已废弃的 PSP：

  • privileged：不限制（系统组件 namespace 用）
  • baseline：禁止明显的特权化（hostNetwork、privileged 容器等）
  • restricted：最严，强制非 root、丢弃 capabilities 等

用 namespace 标签声明：pod-security.kubernetes.io/enforce: restricted。

SecurityContext：单 Pod 的精细控制

securityContext:
  runAsNonRoot: true            # 禁止 root 运行
  readOnlyRootFilesystem: true  # 根文件系统只读，写临时文件走 emptyDir
  allowPrivilegeEscalation: false
  capabilities:
    drop: ["ALL"]               # 丢弃全部 Linux capabilities，按需加回

这四行是「容器逃逸」防线的主力：攻击者即便进了容器，没有 root、没有 capabilities、写不了文件系统，能做的事极其有限。

第四层：NetworkPolicy

Pod 间默认全通。NetworkPolicy 按标签收口：只允许来自前端 namespace 的 80 端口访问后端，其余拒绝。机制与注意点见第 06 章。

串起来：一个最小权限的例子

给「订单服务」做安全加固的完整动作：

  1. 建专属 ServiceAccount，不用 default
  2. RBAC 只给它需要的动词（比如只读某个 ConfigMap）；不需要 API 权限就一个 Binding 都不建
  3. namespace 打 PSA restricted 标签
  4. Pod 里写上面那四行 SecurityContext
  5. NetworkPolicy：只放行网关到它的 8080，和它到数据库的 5432

五步做完，「容器被攻破」到「集群沦陷」之间的路基本被切断。

面试官视角

Q：如何给一个 Pod 最小权限地访问 API？

✕ 平庸答案

「给它一个 ServiceAccount，绑个 cluster-admin 方便调试。」

——反面教材。cluster-admin 绑定是集群里最常见的安全债。

✓ 加分答案

「先建专属 ServiceAccount 并在 Pod 里显式引用；然后从『零权限』出发，按需要加 Role：只给必要 namespace 的必要资源的必要动词，用 RoleBinding 绑定，不用 ClusterRoleBinding 除非确需集群级；用 kubectl auth can-i 验证。若应用根本不需要访问 API，就保持零权限并关掉 token 自动挂载（automountServiceAccountToken: false）。」

常见误区

误区一：Namespace 之间默认隔离

名字与配额隔离而已。网络默认全通、RBAC 默认按 ClusterRole 可跨 namespace 授权。隔离要显式建。

误区二：RBAC 配好 = Pod 安全

RBAC 管的是「对 API 能做什么」。容器内的进程是否 root、能否逃逸，是 SecurityContext / PSA 的事。两层独立。

误区三：Secret 存了就安全

base64 不是加密（第 08 章）。能 list secret 的人等于拿到明文。Secret 的安全 = RBAC + etcd 静态加密 + 传输 TLS 三者之和。
