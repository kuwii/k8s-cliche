调度与资源

两个问题：装不装得下（resources / QoS），放哪儿（filter / score / 亲和 / 污点）。

一句话答案

requests 是调度依据与最低保障，limits 是使用上限；两者组合决定 QoS 等级，QoS 决定节点压力时谁先被驱逐。 placement 侧则是：过滤（硬性条件）→ 打分（软性偏好）→ 绑定。

requests 与 limits 的准确语义

resources:
  requests:
    cpu: 250m       # 0.25 核；调度器按它找放得下的节点
    memory: 256Mi   # 节点内存「账面」扣减它
  limits:
    cpu: 1000m      # 超过就被节流（throttle），不杀
    memory: 512Mi   # 超过就 OOM Kill
  • CPU 是可压缩资源：超 limit 的表现是被节流（CFS quota，进程变慢但不死）
  • 内存是不可压缩资源：超 limit 的表现是被 OOM Kill（进程死）
  • requests 只影响调度时的账面计算和 cgroup 的最低份额；节点超卖（requests 之和 > 实际容量）是常态，赌的是大家不同时用满
社区实践争议点

不少团队不设 CPU limit：CPU 节流造成的延迟毛刺比「多占一点 CPU」危害更大，而 CPU 超用不会压垮节点。内存 limit 则普遍设置（防止单 Pod 吃垮节点）。面试时能说出这个权衡，比背定义强。

QoS 三档与驱逐顺序

等级条件节点内存压力时
Guaranteed所有容器 cpu/memory 的 requests == limits最后被驱逐
Burstable设了 requests 但不满足 Guaranteed居中
BestEffort什么都没设最先被驱逐

驱逐（Eviction）是 kubelet 在节点资源压力下的主动行为：按 QoS 等级 + 超用比例挑 Pod 杀掉腾空间，Pod 状态变为 Evicted。它与 OOM Kill 的区别：OOM Kill 是单容器超自己的 limit；驱逐是节点级压力下的取舍。

放置：过滤 → 打分

  • Filter 的依据：节点剩余资源是否 ≥ requests、污点是否被容忍、nodeSelector / 节点亲和的硬性要求、卷能否挂载
  • Score 的依据：资源均衡度、亲和的软性偏好、拓扑分布等

表达 placement 意愿的四种手段

手段粒度硬/软
nodeSelector节点标签精确匹配硬（最简单）
nodeAffinity节点标签表达式required（硬）/ preferred（软）
podAffinity / podAntiAffinity相对其他 Pod 的位置（同区/避开）required / preferred
topologySpreadConstraints跨拓扑域（zone/节点）的均匀度maxSkew 控制

podAntiAffinity 说「别和我同节点」，topologySpreadConstraints 说「各 zone 数量差不能超过 1」——后者是「分布均匀」的直接表达，前者只是 pairwise 的排斥。

污点与容忍：节点拒客的艺术

亲和性是 Pod 说「我想去哪」；污点是节点说「我不想接谁」。节点打污点，Pod 带相应容忍才能进入。

effect含义
NoSchedule新 Pod 不调度上来（已有的不动）
PreferNoSchedule尽量不调度上来（软性）
NoExecute不容忍的 Pod 立刻被驱逐（已有的也赶）

control-plane 节点默认带污点，所以业务 Pod 不会落上去；节点故障时 Node 控制器会给它打 node.kubernetes.io/unreachable 的 NoExecute 污点——这就是「节点挂了 Pod 被赶走重建」的机制。

面试官视角

Q：requests 和 limits 的区别？怎么设置？

✕ 平庸答案

「requests 是最小值，limits 是最大值。」

——没说清「最小」对谁而言（调度账面）、CPU 与内存超限的不同后果、QoS 与驱逐的关联。

✓ 加分答案

「requests 是调度器选节点的依据，也是 cgroup 的最低保障；limits 是上限。关键区别在超限后果：CPU 超 limit 被节流、变慢不死；内存超 limit 被 OOM Kill。两者组合决定 QoS 等级，而 QoS 决定节点内存压力时的驱逐顺序——BestEffort 先死，Guaranteed 最后死。设置上我倾向 requests 贴近真实 P99 用量、内存设 limit 防吃垮节点、CPU limit 谨慎或不设以避免节流毛刺。」

常见误区

误区一：limits 设得越大越安全

内存 limit 过大 = 单 Pod 可能吃垮节点；且 requests 低 limits 高会落入 Burstable，驱逐时比 Guaranteed 先死。安全来自匹配，不来自大。

误区二：写了 preferred 亲和性就一定会遵守

preferred 是打分偏好，资源紧张时完全可能被忽略。硬约束用 required，但 required 写错会导致 Pod 永远 Pending。

误区三：Pod 被 Evicted = 应用有 bug

驱逐是节点压力下的资源决策，与应用对错无关。查 kubectl describe node 的压力条件与 QoS 分布，而不是查代码。
