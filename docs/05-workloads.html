工作负载

工作负载（Workload）回答一个问题：你的容器该「怎么跑」。

一句话答案

四种答案对应四种对象：无状态 → Deployment，有状态 → StatefulSet，每节点一份 → DaemonSet，跑完就结束 → Job / CronJob。

选型是一道四选一：副本之间可否互换？副本数由谁定？要不要跑完就停？

先回到 Pod：为什么它是最小单位

Pod 不是「一个容器」，而是一个共享网络命名空间和存储卷的容器组（第 04 章）。同 Pod 内容器共享一个 IP、互用 localhost 通信、共享挂载卷——它们是「同生共死的一组进程」。

这个设计支撑了 sidecar 模式：日志收集器、服务网格代理、配置刷新器，都作为「配角容器」和主容器住在同一个 Pod 里。

实践准则

几乎不要裸建 Pod。裸 Pod 死了就死了，没人补。永远让某个工作负载对象（哪怕只是 Deployment）持有它——这样控制循环才接得住。

Deployment：无状态的标准答案

你声明副本数和 Pod 模板，它保证：副本数维持、滚动更新、可回滚。

滚动更新是怎么滚的

改 Pod 模板（比如镜像版本）时，Deployment 创建一个新的 ReplicaSet，然后交替伸缩：新 RS 加一点、旧 RS 减一点，直到全部切换。节奏由两个参数控制：

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 25%        # 更新期间最多可以「超出」期望副本数的数量
    maxUnavailable: 25%  # 更新期间最多可以「不可用」的数量

期望 4 副本、两个 25% 都向上取整为 1：更新时最多同时存在 5 个 Pod，最多 1 个不可用。这两个数决定了更新速度与可用性的权衡，面试爱考计算。

回滚之所以快，是因为旧 ReplicaSet 只是被缩到 0、对象还在：kubectl rollout undo 把流量权重切回去即可。

StatefulSet：给「有身份」的应用

数据库、消息队列这类应用，副本之间不可互换：主从角色不同、各自数据不同。StatefulSet 提供三个稳定保证：

  • 稳定网络标识：Pod 名是 web-0、web-1、web-2，重建后名字不变；配合 headless Service，每个 Pod 有独立 DNS 名
  • 稳定存储：volumeClaimTemplates 给每个 Pod 自动创建专属 PVC，Pod 重建后挂回自己原来那块盘
  • 有序部署与伸缩：按序号逐个启动 / 逆序逐个删除
StatefulSet 不替你管数据

它保证的是「盘跟着 Pod 走」，不保证数据复制。主从同步、分片、quorum 仍是应用自己的事。把 StatefulSet 当成「自动数据高可用」是危险误解。

DaemonSet：拓扑决定副本数

每个节点（或满足节点选择条件的节点）恰好跑一个 Pod。典型：日志采集（node-exporter、fluentd）、监控 agent、kube-proxy 本身。

特征：没有 replicas 字段——副本数由节点拓扑决定，加节点自动加 Pod。

Job / CronJob：跑完就结束

前面三种都假设进程「应该一直活着」，进程退出就是异常。Job 反过来：退出才是成功。

  • completions：总共要成功几次；parallelism：同时跑几个
  • backoffLimit：失败重试上限，超过则 Job 判失败
  • CronJob = Job + schedule（cron 表达式）+ concurrencyPolicy（Allow / Forbid / Replace，控制上一次没跑完时怎么办）

选型表

你的需求选择
Web 服务、API、无状态微服务Deployment
MySQL 主从、ZooKeeper、Kafka、Redis 集群StatefulSet
每节点都要有的 agent（日志/监控/网络插件）DaemonSet
数据批处理、迁移任务、一次性计算Job
每天凌晨跑报表CronJob

面试官视角

Q：Deployment 的滚动更新过程？

✕ 平庸答案

「逐个替换旧 Pod 为新 Pod。」

——漏了机制：新 ReplicaSet、交替伸缩、maxSurge/maxUnavailable、可回滚的原因。

✓ 加分答案

「改模板会触发新建一个 ReplicaSet，控制器按 maxSurge 和 maxUnavailable 交替伸缩新旧两个 RS：先起新、就绪后再缩旧，保证过程中可用副本不低于下限。旧 RS 缩到 0 但对象保留，所以 rollout undo 回滚几乎是瞬时切换。 readiness 探针在这里是关键——新 Pod 不通 readiness 就不会被计入可用，更新会卡住而不是带病上线。」

Q：StatefulSet 和 Deployment 的区别？——答「三个稳定」：稳定网络标识、稳定存储（volumeClaimTemplates）、有序部署伸缩；并补一句「数据复制仍是应用自己的责任」，立刻区分于背答案的人。

常见误区

误区一：StatefulSet 会自动做数据高可用

它只保证 PVC 跟着 Pod 走。主从同步、故障切换是应用层职责。

误区二：给 DaemonSet 设 replicas

没有这个字段。副本数 = 匹配污点/选择器的节点数。

误区三：Job 的 Pod 跑完会被立刻删掉

默认保留（Completed 状态），供查日志与审计。要清理靠 ttlSecondsAfterFinished 或手动。
